## Why this matters

`pnpm audit --prod` currently reports 6 known vulnerabilities, all in
transitive dependencies (nothing directly listed in `package.json`'s own
`dependencies` is vulnerable):

```
4 × HIGH   fast-uri  (via @hookform/resolvers > ajv > fast-uri)
           - host confusion via skipped IDN canonicalization on scheme-relative references
           - server-side request forgery via malformed IPv6 normalization
           - server-side request forgery via repeated hostname percent-decoding
           - host confusion via percent-encoded scheme normalization
2 × MODERATE  qs  (via express > qs)
           - array-limit bypass via bracket-key comma parsing
           - Denial of Service via Attacker Controlled isBuffer
```

This app is deployed publicly (Render, per `CLAUDE.md`'s Deployment
section) behind HTTP Basic Auth — still real, internet-reachable attack
surface for anyone who can send it a crafted request (with or without
valid credentials; several of these are pre-auth-parseable input paths).
The third `/improve` pass (2026-08-27) confirmed `pnpm audit --prod`
clean at the time — these are newly disclosed or newly resolved since,
not something introduced by any of this session's own changes.

Both vulnerable packages are two to three levels deep in the dependency
tree (`fast-uri` via `@hookform/resolvers → ajv`, `qs` via `express`),
confirmed via `pnpm-lock.yaml`: resolved versions are `fast-uri@3.1.5`
(needs `>=3.1.6`) and `qs@6.15.3` (needs `>=6.16.0`). Neither `express`
nor `@hookform/resolvers` themselves need a version bump for this —
pnpm's `overrides` field can force just the vulnerable transitive
packages up to a patched version without touching either direct
dependency's declared range, which is the lowest-risk fix available
(patch-level bumps within packages this app never imports directly).

## Steps

### Step 1: Add `pnpm.overrides` forcing both packages to patched versions

Add this field to `package.json`, at the top level (alongside
`"scripts"`, `"dependencies"`, etc. — exact position doesn't matter,
place it near `"packageManager"` for locality):

```json
  "pnpm": {
    "overrides": {
      "qs": ">=6.16.0",
      "fast-uri": ">=3.1.6"
    }
  },
```

**Verify**: `pnpm check` → exits 0 (this step alone doesn't yet change
the lockfile — Step 2 does; this check just confirms the JSON edit
didn't break anything parsing `package.json`).

### Step 2: Reinstall to apply the overrides and regenerate the lockfile

Run `pnpm install`.

**Verify**: exits 0. `grep -A2 "^  qs@" pnpm-lock.yaml` → resolved
version is `>= 6.16.0`. `grep -A2 "^  fast-uri@" pnpm-lock.yaml` →
resolved version is `>= 3.1.6`.

### Step 3: Confirm the audit is clean and nothing else broke

**Verify**: `pnpm audit --prod` → "No known vulnerabilities found" (or
equivalent zero-count output). `pnpm check` → exits 0, same baseline as
before this plan (confirm via `git stash` + `pnpm check` on the
unmodified tree first if you need a baseline to compare against — this
repo has had a clean `pnpm check` baseline since plan 018, per
`plans/README.md`'s history, so any errors here are new and worth
investigating before proceeding). `pnpm test` → all pass, same count as
before this plan. `pnpm build` → exits 0, `dist/index.cjs` and
`dist/public/` produced.

## Test plan

No new test files — this is a dependency-resolution fix, not application
logic. The verification *is* the audit output plus the existing full
test/build suite passing unchanged, which is the correct and complete
check for a transitive-version bump with no application code touched.

1. `pnpm audit --prod` — the direct regression check for this plan's
   entire purpose.
2. `pnpm test` — confirm no behavioral regression from the version bump
   (unlikely for these specific patch/minor-level security fixes, but
   free to check).
3. `pnpm build` then, if convenient, `pnpm dev` and a quick manual smoke
   test — load the Dashboard, submit any form that goes through
   `@hookform/resolvers` (e.g. Add Bill), confirm it still validates and
   submits correctly. `fast-uri`/`ajv` sit underneath the app's
   `zodResolver` form-validation path; this is the one place a
   transitive bump in that chain could theoretically surface a
   behavioral difference, worth one manual check even though the
   audit/test suite alone would likely catch a real break.

**Verify**: all 3 above hold as described.

## Maintenance notes

- `pnpm.overrides` pins these two packages at "at least" the patched
  version regardless of what future direct-dependency bumps would
  otherwise resolve to — if `express` or `@hookform/resolvers` are ever
  majorly upgraded and naturally pull in a `qs`/`fast-uri` version well
  past what's pinned here, the override is harmless (still satisfies
  `>=`) and can be removed for cleanliness at that point, not required.
- Re-run `pnpm audit --prod` periodically (or as part of a future CI
  step — `plans/019-add-test-harness-and-ci.md`'s workflow doesn't
  currently include an audit gate) to catch the next drift before it
  needs a manual `/improve` pass to surface it again.
